# P5.3 — Analytics and Statistics

Status: **PLANNED**

**Read with:** the brief for the events being recorded.

All systems publish meaningful post-commit state transitions through one versioned server-side `EventRecorder` boundary. A logical event has a stable name/schema version, unique ID, server timestamp, user/session IDs, content/balance version, stable content IDs, numeric value where useful, and a small validated property set.

Record action batches and stop reasons, item/economy transactions, encounter/run summaries, progression/unlocks, return reports, onboarding/adoption, rare discoveries, and entitlement/purchase processing. Do not record frames, progress ticks, every automatic attack, personal information, chat, or unbounded free-form text.

Composable sinks provide bounded durable statistics, curated/batched Roblox analytics, Studio/test diagnostics, and a possible future external warehouse. DataStores are not raw event logs; leaderboards use separately validated projections.

Emit only after the gameplay transaction commits. Recorder failure never rolls back valid gameplay, but returns an explicit observability result and increments bounded error telemetry. Tests use a deterministic in-memory recorder.
